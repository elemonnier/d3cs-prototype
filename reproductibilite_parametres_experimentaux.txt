1. PARAMETRES CRYPTOGRAPHIQUES
------------------------------

Versions resolues dans Cargo.lock :

ark-bls12-381 0.4.0
ark-ec        0.4.2
ark-ff        0.4.2
ark-serialize 0.4.2
ark-std       0.4.0
aes-gcm       0.10.3
base64        0.21.7
rand          0.8.5
rand_core     0.6.4
serde_json    1.0.149
sha2          0.10.9

Le CP-ABE utilise G1Projective/G1Affine, G2Projective/G2Affine, Fq12 pour GT,
Fr pour les scalaires et Bls12_381::pairing pour G1 x G2 vers GT.

L'ABS utilise egalement BLS12-381 : g et g1 sont dans G2, g2 est dans G1 et z est dans GT.

Serialisation elementaire avec ark_serialize::CanonicalSerialize en mode compresse :

scalaire Fr                 : 32 octets
element compresse de G1    : 48 octets
element compresse de G2    : 96 octets
element compresse de GT    : 576 octets

Les valeurs sont encodees en Base64 sans padding avec STANDARD_NO_PAD, puis les structures
completes sont serialisees avec serde_json.

Hachage CP-ABE : SHA-256 des attributs, converti en Fr.
Derivation de cle symetrique : SHA-256 de la serialisation compressee d'un element GT.
Hachage ABS : hash-to-curve vers G1 avec SHA-256 et les domaines D3CS-ABS-H1 et D3CS-ABS-H2.

Chiffrement symetrique : AES-256-GCM, cle de 32 octets et nonce aleatoire de 12 octets.
La source d'alea est rand_core::OsRng.

6. CAMPAGNE MULTI-SAULTS
-------------------------

Fichiers : scripts/multihop_latency.py et scripts/merge_multihop_results.py

Configurations finales : 1, 2, 3, 4, 5 et 10 sauts.
La configuration 20 sauts est exclue des resultats finaux.

H sauts correspondent a H+1 noeuds :

1 saut  : 2 noeuds
2 sauts : 3 noeuds
3 sauts : 4 noeuds
4 sauts : 5 noeuds
5 sauts : 6 noeuds
10 sauts: 11 noeuds

Topologie : chaine statique N00 -> N01 -> ... -> NH.
N00 est Authority et les autres noeuds sont U1, U2, etc.
Coordonnees : (i x 50, 0).
Espacement : 50 m.
Portee LEPTON : 60 m.
Voisins directs : uniquement les noeuds adjacents.
Mobilite : false.

Parametres LEPTON generes par le script :

jitter=0
time_margin=0
nodes_deferred=0
accel=1
range=60
period=1.0
duration=-1
make_edges=false
edge_default_status=DISCONNECTED
node_default_status=NONE

La campagne est une chaine statique controlee. Le script ne configure pas de coupures ou de
reconnexions temporelles ; il ne s'agit pas d'un scenario intermittent store-carry-forward.

Version LEPTON : 1.0.
Version DoDWAN identifiable : dodwan-4.1.jar.
Plugins : dodwan-napi,dodwan-napi-ws.

Workflows : CT_SHARE, ARL_UPDATE et KEY_REQUEST_RESPONSE.
Warmups : 5 par groupe.
Mesures : 30 par groupe.

Pour CT_SHARE et ARL_UPDATE, la latence est la difference entre le timestamp SystemTime de
l'emission et le timestamp de reception apres traitement reussi de la trame.

Pour KEY_REQUEST_RESPONSE, le chronometrage utilise Instant depuis l'emission de la demande
jusqu'au traitement reussi de USER_KEYGEN par le demandeur.

Un succes correspond a :

- CT_SHARE recu et traite par le destinataire ;
- ARL_UPDATE recu, deserialize et applique sans erreur ;
- KEY_REQUEST ayant produit une reponse USER_KEYGEN correspondante.

Le taux de livraison est : 100 x n_success / n_total.
Les statistiques de latence utilisent uniquement les succes.

Les resultats actuellement presents indiquent 30 succes sur 30 pour chaque groupe 1-5 et
10 sauts, soit 100 % de livraison.

9. COMMANDES DE REPRODUCTION
-----------------------------

Prerequis de compilation :

cargo build --release --bins

CP-ABE :

cargo run --release --bin cpabe_timings

ABS :

cargo run --release --bin abs_timings

Messages reseau, ARL et CT_SHARE :

cargo run --release --bin network_sizes

Stockage du TM :

cargo run --release --bin tm_storage_sizes

Multi-sauts 1 a 5 :

PYTHONIOENCODING=utf-8 python3 -u scripts/multihop_latency.py --warmups 5 --measurements 30 --hops 1,2,3,4,5 --output benchmark_results/multihop

Multi-sauts 10 :

PYTHONIOENCODING=utf-8 python3 -u scripts/multihop_latency.py --warmups 5 --measurements 30 --hops 10 --output benchmark_results/multihop_final_10

Fusion des resultats 1-5 et 10 :

python3 scripts/merge_multihop_results.py --existing benchmark_results/multihop --additional benchmark_results/multihop_final_10 --output benchmark_results/multihop


PARTIE C - INCERTITUDES ET INFORMATIONS NON VERIFIABLES
========================================================

- Le nombre de coeurs physiques et la RAM sont observes dans l'environnement WSL courant.
- La version exacte de WSL2 n'est pas fixee par un fichier du projet.
- La version LEPTON est explicitement indiquee comme 1.0.
- La version DoDWAN est deduite de dodwan-4.1.jar.
- Le depot ne fixe pas une version Python dans un fichier d'environnement.
- Le script multi-sauts genere les configurations LEPTON au moment de l'execution.
- Les pertes, delais artificiels, debits et MTU ne sont pas explicitement configures.
- La campagne multi-sauts est statique et ne simule pas explicitement des partitions ou de la
  mobilite store-carry-forward.
- L'URL GitLab verifiable est : git@gitlab.inria.fr:elemonni/d3cs-prototype.git
- Une URL HTTPS n'est pas enregistree explicitement dans le depot local.
- La mesure de stockage du TM est une mesure logique serialisee, et non une mesure de RAM ou
  d'espace disque physique.
